## 当前状态：前端已摘除（2026-11-17 14:00）

`package.json` 里的 `dsh.client` 声明**已移除**，左栏「鲸鲸桥接」入口不再出现。

**为什么摘**：入口本身能出来，但面板里三个数字是坏的——
- 「回答方式」把真思考显示成「回声测试」（文案判断错）
- 「正在回复 / 排队」恒为 0（数据源是宿主空壳引擎，见 B-3）

**为什么不是删掉**：这三个问题都出在**数据源**上，不是功能坏了。桥接本身照常工作，微信消息照常由 DSH 处理。

**留了什么**：
| 组件 | 状态 |
|---|---|
| `plugin/apply.mjs`（宿主半边：路由 + 桥接守护） | ✅ 保留并加载 |
| `plugin/index.js`（设置路由处理） | ✅ 保留 |
| `src/`（引擎、代理、supervisor、隔离） | ✅ 保留 |
| `scripts/`（wire-host、自检） | ✅ 保留 |
| `plugin/client.js`（前端界面） | ✅ 文件保留，仅不加载 |
| `package.json` 的 `dsh.client` | ❌ 已摘除，原值存进 `_parked.client.was` |

**恢复方式（等这三个数字修好后再做）**：
```json
"dsh": {
  "bundle": { "patch": "./plugin/cordis.patch.yml" },
  "client": {
    "platform": "web",
    "inject": ["@deepseek-ai/dsh-client-locale", "@deepseek-ai/dsh-client-ui-layout", "@deepseek-ai/dsh-client-ui-sidebar"]
  }
}
```
把 `client` 那一段抄回 `dsh` 下面即可，**不需要动 client.js**。

**恢复后必须验证的三件事**：
1. 左栏入口出现（Console 有 `[whale-bridge] registered sidebar.panellist`）
2. 「回答方式」显示「本机 DSH（委托桥接进程）」
3. 发消息时「正在回复」变成 1 —— **这条是 B-3 的验收点，做不到就别恢复前端**

## 1. 诊断顺序（出问题从第 1 步开始，不跳步）

```powershell
# ── 第 1 步：挂载在位吗 ──────────────────────────────
$P = "I:\DSH-Data\dsh\profiles\desktop"      # ← 不要写死，见 E-1
$j = [IO.File]::ReadAllText("$P\package.json",[Text.Encoding]::UTF8) | ConvertFrom-Json
$j.dependencies.PSObject.Properties | Where-Object { $_.Name -match 'whale' }   # 必须有
$j.dsh.profile.bundles -contains 'whale-dsh-bridge'                            # 必须是 True
Test-Path "$P\node_modules\whale-dsh-bridge"                                   # 必须是 True

# ── 第 2 步：能被解析吗（决定性）─────────────────────
# !! 关键：PowerShell 的反斜杠传进 node -e 会被 JS 当转义吃掉
#    例：'I:\DSH-Data\dsh' 会变成 'I:DSH-Datadsh'  → 必然 FAIL
#    必须先转成正斜杠（见 C-4）
$PJ = $P -replace '\\','/'
node -e "console.log(require.resolve('whale-dsh-bridge',{paths:['$PJ']}))"
node -e "console.log(require.resolve('whale-dsh-bridge/client',{paths:['$PJ']}))"
node -e "console.log(require.resolve('whale-dsh-bridge/cordis.patch.yml',{paths:['$PJ']}))"
# 三个都必须打印出真实路径。任何一个 FAIL → 前端永远不会加载，别往下查了
# 若三个全 FAIL 但前端明明是能跑的，先怀疑自己忘了转正斜杠，别去改插件

# ── 第 3 步：host 半边活着吗 ─────────────────────────
Invoke-WebRequest "http://127.0.0.1:<端口>/plugins/dsh-whale-bridge/service" -UseBasicParsing
# 200 = 后端 OK。注意：这只证明 host，与前端无关（见 G-1）

# ── 第 4 步：前端到底执行了没有（唯一真相）───────────
# 打开 DSH → F12 → Console，找自己插件的日志
# 什么都不打印 → 回第 2 步
# 有日志但入口不出 → 查槽位注册（§2 的 B、F 组）
```

**为什么必须按这个顺序**：前 3 步我可以用命令行验证，第 4 步只能人肉看。**能自动验的必须先验完，不要拿人的时间去试错。**

## 2. 错误索引（症状 → 根因 → 判据 → 修法）

### A 组：前端从未加载（最贵，踩了 5 次）

#### A-1 `exports` 缺 `"./client"` 条目
- **症状**：设置页和侧栏都空，Console 里连一行自己的日志都没有，也没有报错
- **根因**：DSH 找客户端入口走的是 `<包名>/client` 这个子路径。没有 `exports["./client"]`，Node 解析直接 `MODULE_NOT_FOUND`，loader 静默跳过
- **判据**：`require.resolve('<包名>/client')` 抛 `MODULE_NOT_FOUND`
- **修法**：
  ```json
  "exports": {
    ".": "./plugin/apply.mjs",
    "./client": "./plugin/client.js",
    "./cordis.patch.yml": "./plugin/cordis.patch.yml",
    "./package.json": "./package.json",
    "./*": "./*"
  }
  ```

#### A-2 `exports` 缺 `"./*": "./*"` 通配
- **症状**：同上，或加载到一半失败
- **根因**：`exports` 一旦声明就变成白名单，清单外的子路径全部拒绝
- **判据**：解析 `'<包名>/package.json'` 或任意子文件失败
- **修法**：加 `"./*": "./*"`

#### A-3 注册 id ≠ 包名（**最容易犯，我今天又犯**）
- **症状**：Console 报 `Uncaught Error: client-modules: duplicate factory registration for "<某个包名>"`，整包被丢弃
- **根因**：`client.js` 里 `window.__ModuleLoader__.load({ id: 'X' })` 的 `X` 必须等于 `package.json` 的 `name`。不等时 loader 认为这份注册没有归属，反复注册直到崩
- **判据**：
  ```powershell
  # 两个值必须字符级相同
  (Get-Content package.json -Raw | ConvertFrom-Json).name
  Select-String client.js -Pattern "load\(\{[\s\S]*?id:\s*'([^']+)'"
  ```
- **修法**：改包名时，**六个地方一起改**：
  1. `package.json` 的 `name`
  2. `client.js` 的 `load({ id })`
  3. `node_modules` 里的目录名 / junction 名
  4. profile `package.json` 的 `dependencies` 键
  5. profile `package.json` 的 `dsh.profile.bundles` 条目
  6. 插件自带 `plugin/cordis.patch.yml` 里 `- insert: - name:`
- **旁证**：崩溃日志里被点名的那个包名，往往**不是真实包名**，而是写错的 id。看到不存在的包名就去找 id

#### A-4 重复注册（bundles + 主 patch 双份）
- **症状**：同 A-3，`duplicate factory registration`
- **根因**：`dsh.profile.bundles` 已经加载整个包，插件自己的 `plugin/cordis.patch.yml` 会被 `dsh.bundle.patch` 自动应用。**这时主 `cordis.patch.yml` 里绝不能再写一遍这个包的 `- id:` 行**
- **判据**：
  ```powershell
  # 主 patch 里出现自己包名 = 错
  Select-String "cordis.patch.yml" -Pattern 'whale'
  # 应输出空
  ```
- **修法**：删掉主 patch 里那几行。**一个包只能有一个加载源。**

### B 组：加载了但渲染崩

#### B-1 React error #130（element type invalid）
- **症状**：Console 报 `Minified React error #130`，位置在 `slot entry crashed in '<槽位名>'`
- **根因**：传给 `ctx.slots.register({...}, Component)` 的 `Component` 是 `undefined`。通常是组件在 `apply()` 作用域外定义、或依赖的 `require()` 拿到空
- **判据**：报错信息里有具体槽位名，说明注册调用本身跑到了，是组件值有问题
- **修法**：确认组件函数与注册代码在**同一个 factory 闭包内**；`require('react')` 必须在 factory 顶部执行

#### B-2 `trySlot` 静默吞错
- **症状**：什么错都看不到，就是没入口
- **根因**：注册用 `try/catch` 包住但没打印，错误消失
- **判据**：Console 里没有 `console.error`
- **修法**：catch 里必须 `console.error('[<前缀>] ' + name + ' FAILED', error)`

#### B-3 面板状态读错数据源（**2026-11-17 用户实测发现**）
- **症状**：设置页底部「正在回复 0 条 · 排队 0 条」永远是 0，发消息时也不变；「回答方式」把真思考显示成「回声测试」
- **根因**：这个插件是**双进程**架构——
  - 宿主半边（`plugin/apply.mjs`）的 `engine.adapter` 是 `{ kind: 'delegated' }`，**它永远不处理消息**，`active`/`pending` 恒为 0
  - 真实消息由鲸鲸直接 POST 到**独立桥接进程**（`src/proxy.mjs`，端口在 `service.json` 之外由 supervisor 分配）
  - 所以面板去问宿主 = 问一个空壳
- **判据**：
  ```powershell
  # 宿主返回的 adapter 是 delegated，不是 acp
  Invoke-WebRequest "http://127.0.0.1:<DSH端口>/plugins/dsh-whale-bridge/status" -UseBasicParsing
  # {"status":{"enabled":true,...,"adapter":"delegated","active":0,"pending":0}}
  ```
- **修法（三处配合）**：
  1. `src/proxy.mjs` 增加 `GET /status`，返回 `engine.status()`（带 Bearer 鉴权）
  2. `src/supervisor.mjs` 增加 `liveStatus()`，用 `this.listening.url/token` 去 fetch 子进程的 `/status`
  3. `plugin/index.js` 的 status 分支合并：`{ ...local, ...(await supervisor.liveStatus()) }`
- **前端文案同步**：`client.js` 的判断要把 `'delegated'` 也当作真思考——
  ```js
  (status.adapter === 'acp' || status.adapter === 'delegated') ? '本机 DSH' : '回声测试'
  ```
- **通用教训**：**双进程/子进程架构里，任何「运行中」的指标都必须问真正干活的那个进程。** 宿主自己的计数器只反映它自己的流量，通常是零。

### C 组：配置文件写坏

#### C-1 JSON 带 BOM
- **症状**：DSH 完全起不来，或 `dsh plugin install` 报 `JSON.parse` 失败
- **根因**：PowerShell 的 `Set-Content -Encoding UTF8` 在 PS 5.1 下**加 BOM**
- **判据**：
  ```powershell
  $b=[IO.File]::ReadAllBytes($path); $b[0..2] -join ','
  # 239,187,191 = 有 BOM = 错
  ```
- **修法**：
  ```powershell
  [IO.File]::WriteAllText($path, $json, (New-Object Text.UTF8Encoding($false)))
  ```

#### C-2 `.ps1` 缺 BOM
- **症状**：脚本里中文全乱码，路径解析失败
- **根因**：PS 5.1 按 ANSI 读无 BOM 的脚本
- **修法**：`.ps1` 反过来要**有** BOM

#### C-3 YAML 改坏
- **症状**：DSH 起不来，且没有明显报错
- **判据**：`python -c "import yaml; yaml.safe_load(open(p,encoding='utf-8').read())"`
- **修法**：改完必须解析一次再重启

#### C-4 反斜杠喂给 `node -e` 会被当转义吃掉（**2026-11-17 实测踩到**）
- **症状**：`require.resolve(..., {paths:['I:\DSH-Data\dsh\profiles\desktop']})` 三个入口全报 `MODULE_NOT_FOUND`，但前端明明是好的
- **根因**：Windows 路径的 `\D` `\d` `\p` 在 JS 字符串里是转义序列，被吃掉
  ```
  实际传进去的: console.log('I:\DSH-Data\dsh\profiles\desktop')
  真正看到的:   I:DSH-Datadshprofilesdesktop
  ```
- **判据**：单独跑一句 `node -e "console.log('I:\DSH-Data')"`，看输出是不是少了反斜杠
- **修法**：
  ```powershell
  $PJ = $P -replace '\\','/'     # PowerShell 侧先转正斜杠
  node -e "require.resolve('pkg',{paths:['$PJ']})"
  ```
- **教训**：**报错先怀疑自己的验尸工具，再怀疑被验的东西。** 这个坑害我差点去改一个本来没坏的插件。

### D 组：写死路径

#### D-1 硬编码 DSH 数据目录
- **症状**：自己机器能跑，别人装机即坏
- **历史**：`WHALE_BRIDGE_LIVE_PROFILE || 'I:\\DSH-Data\\dsh\\profiles\\desktop'`
- **修法**：从 `DSH_HOME` 或 `~/.dsh` 推导
  ```js
  function liveProfilePath() {
    const home = process.env.DSH_HOME || path.join(os.homedir(), '.dsh')
    return path.join(home, 'profiles', 'desktop')
  }
  ```

#### D-2 硬编码用户名
- **症状**：同上
- **修法**：`os.homedir()`，永远不要写 `C:\Users\Administrator`

### E 组：错误兜底掩盖问题

#### E-1 `?? '默认值'` 兜底
- **症状**：功能悄悄失效，用户永远看不出区别
- **历史**：`process.env.WHALE_BRIDGE_ADAPTER ?? 'mock'` → 父进程传错就一直用模拟适配器，界面显示正常
- **修法**：**配置文件的优先级高于环境变量**；配置缺失就抛错，不要塞兜底值

#### E-2 子进程盲信父进程环境
- **症状**：父进程传了错值，子进程照单全收
- **修法**：子进程重新读配置文件，不完全信任环境变量

### F 组：槽位与注入

#### F-1 `client.inject` 缺槽位所属模块
- **症状**：`ctx.slots.inject('<槽位>', ...)` 静默失败，无报错
- **根因**：不同槽位归不同内置模块管，不在 `inject` 里声明就拿不到
- **对照表**：

  | 想用的槽位 | 必须 inject |
  |---|---|
  | `settings.section` | `@deepseek-ai/dsh-client-ui-slots` |
  | `sidebar.panellist`（左侧栏） | `@deepseek-ai/dsh-client-ui-sidebar` |
  | `sidebar.right.pane.tab`（右侧栏） | `@deepseek-ai/dsh-client-ui-sidebar-right` |
  | `conversation.*` | `@deepseek-ai/dsh-client-ui-conversation` |

- **判据**：找不到就抄同机已工作的插件，**不要自己推**
  - 左侧栏 → 抄 `dsh-phone`
  - 右侧栏 → 抄 `dsh-context`
- **注意**：这些是 DSH 内置虚拟模块，**不在 node_modules 里**，写名字就行，别去找文件

#### F-2 用 `id` 还是 `key`
- 左侧栏 `sidebar.panellist` 用 `id`
- `main` 槽位用 `key`
- 两者**值必须相同**才能关联（点左侧图标 → 打开对应页面）

### G 组：验证错位（**所有坑的总根因**）

#### G-1 把 HTTP 200 当「前端正常」
- **症状**：后端能响应，前端一片空白
- **根因**：200 只证明 host 半边活着。前端是**浏览器里另加载的一份 JS**，跟 HTTP 状态无关
- **纪律**：host 通 ≠ 前端通。两件事要分别验

#### G-2 把 `/models` 200 当「账单正常」
- **历史**：账单显示 ¥0，我用 `GET /models` 拿到 200 就说「key 没问题」。实际上 200 只证明**钥匙能开门**，不证明门后面在花钱
- **纪律**：验什么就拿什么当判据。问账单就去核账单归属，别拿探活代替

#### G-3 把「文件存在」当「能被加载」
- **纪律**：`Test-Path` 成立 ≠ `require.resolve` 成立 ≠ 浏览器实际执行。三级验证，一级都不能省

#### G-4 用「这次不是猜的」当开场白，然后接着猜
- **纪律**：**真正的「不是猜」是命令行打印出了结果，不是把话说得更用力。** 说这句话之前先问自己：我跑了什么命令？

## 4. 版本更新时的对照流程

改任何东西之前，先回答三个问题：

```
1. 这次改动会碰到六处命名里的哪一个？
   → 碰到一个，就要检查其余五个是否受影响

2. 这次改动会不会改变加载路径？
   （移动文件、改 exports、改 dsh.bundle.patch）
   → 改了就跑 §3 第 2、3 步

3. 这次改动有没有可能让「已经能跑的东西」变坏？
   → 有，就先存回档，改完再跑完整清单
```

**历史教训**：11-17 我把包名从 `whale-dsh-bridge` 改成 `dsh-whale-bridge`，觉得「只是改个名字」。结果六个地方只改了一个，插件整个消失，凌霜重启了五次、骂到要删人。**改名从来不是「只是改个名字」。**

## 5. 附录：本机关键路径

| 项 | 值 |
|---|---|
| DSH profile（桌面端实际使用） | `I:\DSH-Data\dsh\profiles\desktop` |
| `C:\Users\Administrator\.dsh` | 上面那个目录的 Junction，**同一份数据** |
| 插件源码 | `I:\DeepSeek Harness工作区\程序开发\whale-dsh-bridge` |
| 插件安装副本 | `I:\DSH-Data\plugins\whale-dsh-bridge` |
| 回档工具 | `E:\桌面\DSH回档\`（**一个字都不许改**） |
| 桥接运行数据 | `C:\Users\Administrator\.whale-dsh-bridge\` |
| 桌面端主进程 cmdline 里的 profile | `C:\Users\Administrator\.dsh\profiles\desktop` |
| 运行内嵌 Python | `C:\Users\Administrator\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe` |
| Node | `I:\Node\node.exe` |

**两个环境别名（容易误判）**：
- `C:\Users\Administrator\.dsh` = `I:\DSH-Data\dsh`（junction），改哪个都一样
- `E:\桌面` 才是真桌面，`C:\Users\Administrator\Desktop` 他看不到
