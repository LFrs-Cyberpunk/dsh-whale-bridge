### ⚠️ 2026-11-14 更正：运行时根本不读 `plugin.json`

重新核对 4.1.2 源码后发现一件比"键名大小写"严重得多的事：

```js
// messagePlugins.js:121-136
fs.readdirSync(this.root).filter(name => name.endsWith('.flow.json'))
  const id = name.slice(0, -10);
  const flow = readJson(path.join(this.root, name));
  if (flow.id !== id || flow.api !== 3 || ... ) return [];
  const grant = readJson(path.join(this.root, id + '.flow-grant.json'), 8192);
  if (grant.hash !== hash || !grant.enabled) return [];
```

- `this.root = path.join(dataDir, 'plugins')`（`messagePlugins.js:97`）
- `dataDir = config.paths?.dataDir || <cwd>/data`（`chat.js:204`）
- **运行时只认 `<id>.flow.json` + `<id>.flow-grant.json`**，两者缺一不可
- `grant.hash = sha256(JSON.stringify(flow))`，内容改一个字授权立刻失效
- **整个 `src` 里没有任何 ZIP 解压 / 安装器代码**，`data/plugins` 目录存在但为空

所以之前的两个 ZIP **不是鲸鲸能直接消费的东西**（可能是市场的分发格式，安装器在别的程序里）。真正能落地的交付是两个 JSON 文件。

已按这个格式产出（`npm run make:flow`）：

| 文件 | 内容 |
|---|---|
| `whale-dsh-router.flow.json` | `{id, api:3, hooks:["chat.prompt","chat.dispatched"], permissions:["model.prompt"], wasm:<base64>}` |
| `whale-dsh-router.flow-grant.json` | `{hash: sha256(JSON.stringify(flow)), enabled: true}` |

目标位置：`I:\Whale-Girl\WhaleGirl\data\plugins\`。

`tests/flow-plugin.test.mjs` 6 项盯着：格式合规、base64 可还原成原始 wasm、hash 与序列化一致、篡改后授权失效、只声明 `model.prompt`、以及 8 种会被静默跳过的错误形态。

## 二-B、鲸鲸 4.1.2 新增的 JavaScript 插件运行时（2026-11-14 查证）

鲸鲸从 4.1.2 起多了一条 JS 插件路线，源码在 `src/services/javascriptPlugins.js`。查证结果如下，**它不改变我们的 WASM 方案，但解释了一个原本没得选的限制**。

| 事实 | 依据 | 对我们的影响 |
|---|---|---|
| JS 插件跑在独立 worker 里，经 IPC 向宿主请能力 | `hostRequest` / `child.send` | 插件本身仍然没有网络 |
| 宿主只暴露 6 个方法 | `pluginHost.js:26` `methods: ['api','capabilities','search','model','send','delivery']` | **发不出任意 HTTP** |
| `api` 方法被钉在插件自己的 API 基址 | `pluginHost.js:76` `new URL(args.url, runtime.pluginApiUrl)` | 打不到我们的本地代理端口 |
| JS 插件用 `system.full` 权限，用户要逐个确认 | `javascriptPlugins.js:72` `flow.permissions[0] !== 'system.full'`；`75` `grant.fullAccess === true` | 权限比 WASM 重得多 |
| 超时 100–120000ms，默认 30000 | `timeout()` | 比 WASM 的 300ms 宽得多，但仍走宿主 |
| 新增钩子 `chat.search` / `chat.search_result` / `app.start` / `app.stop` / `timer.tick` / `tool.run` | `HOOKS = [...WASM_HOOKS, ...]` | **检索前后可插扩展点**，结果可进本轮提示词 |
| WASM 权限校验没变 | `messagePlugins.js:129-131` 仍只接受 `chat.history` / `model.prompt` | 我们的 WASM 包照旧可用 |
| JS 插件有数据目录与持久状态 | `dataDirectory()` / `MAX_STATE = 65536` | 适合放检索索引，不适合放人格 |

**结论**：两条路都进不了任意网络。差别只在**权限重量**和**能不能主动检索**：

- 我们的 WASM 版只要 `model.prompt`（用户确认成本低），负责「把信封写进 system」。
- JS 版要 `system.full`（确认成本高），但能拿 `chat.search` 钩子做记忆检索。

所以首版继续走 WASM。JS 路线留作「记忆检索放进鲸鲸侧」的备选，不是现在。

## 四、DSH ACP（我们是客户端）

### 会话接回（`session/resume`）—— 2026-11-15 实测

「每次开新对话上下文就清空」的根因不是模型，是**桥接重启后忘了会话 id**。实测确认可以接回：

| 方法 | 参数 | 返回 | 结论 |
|---|---|---|---|
| `session/list` | `{ cwd }` | `{ sessions: [{ sessionId, cwd }] }` | 可用，宿主记得已关闭的会话 |
| `session/resume` | **必须** `{ sessionId, cwd, mcpServers }` | **只有 `{ configOptions }`，不含 sessionId** | 可用 |

三个坑：

1. **成功时不返回 `sessionId`**。我最初写成「拿不到 sessionId 就算失败」，于是可用的 resume 一直被当成失败。
2. **缺 `cwd` 或 `mcpServers` → `Invalid params`**。只给 `sessionId` 也不行。
3. **resume 一个已激活的会话 → `session is already active`**。所以一个 id 只能接一次。

已实现：会话 id 落盘（`bridge-sessions.json`），重启后首次使用时先 resume，宿主真忘了才开新会话，并用记忆层的「上次聊到」兜底。

`tests/session-resume.test.mjs` 4 项：id 落盘、重启后接回不换 id、宿主忘了能降级、坏状态文件不炸。

**未验证**：接回后上下文是否真的还在——桩模型永远回同一句，验不了。这需要真模型。
**依据**：`@deepseek-ai/dsh-acp/lib/index.js` + `@agentclientprotocol/sdk/dist/schema/index.js`（从 `app.asar` 只读提取后核对，提取物已删）；**并已在隔离宿主上实测**（`npm run probe:acp`）。

### 实测中踩到的三个坑（都写进代码注释了）
1. **CLI 入口在 `app.asar` 内**，`fs.existsSync` 判断为不存在。只能通过 `dsh.cmd` 启动（Electron 认 asar 路径），不能直接 spawn exe 加 cli.js。
2. **`--profile acp` 是内置模板**，不在 `$DSH_HOME/profiles` 目录里；首次启动会自动创建 profile 目录。
3. **ACP 会话用的模型配置在 `acp` 条目（`provider` / `model`），不在 `agent-default-model`**。改错地方会一直报「no API key for provider route "deepseek-official"」，看起来像凭据问题，其实是没改到生效的位置。

### 怎么复现

```powershell
npm run probe:acp
```

它会自建隔离 `DSH_HOME`、起一个只监听 `127.0.0.1` 的假模型桩、跑完整回合、打印每一步结果、然后杀掉所有子进程。不读你的凭据，不连外网，不碰日常 profile。
